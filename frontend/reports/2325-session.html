2. Cross-cutting findings#

2.1 /events is the bottleneck: 1.05–1.13 s server time, 46 KB uncompressed#

TTFB equals total duration, so this is server time. Analysis in §3.2. Everything users see in the sidebar/timeline waits for it.

2.2 No gzip on any Go /v2 response#

backend/pkg/server/api/responser.go:39-48 writes raw json.Marshal output; no compression middleware anywhere in backend/pkg/server (grep gzip finds only request-body decompression in api/request.go:81-112). Measured with gzip -6 on captured bodies:

Python already compresses ≥1000 B bodies (GZipMiddleware(minimum_size=1000), ee/api/app.py:118), which is why only /projects is gzipped.

2.3 CORS: 11 preflights, none cached for Go routes#

The API lives on api.openreplay.com while the app is on app.openreplay.com, so every request with Authorization triggers an OPTIONS preflight.

  • Go (backend/pkg/server/middleware/builder.go:103-120): sets Access-Control-Allow-Origin: *, Allow-Methods, Allow-Headers, and on OPTIONS a Cache-Control: max-age=86400 — but no Access-Control-Max-Age, which is the only header the browser's preflight cache honours. Result: a preflight on every Go call, forever. Note backend/pkg/server/api/middleware.go:21 corsMiddleware is dead code; the live one is in builder.go.
  • Python (ee/api/app.py:165-175): allow_origins=["*"] with allow_credentials=True. Starlette then reflects the request Origin and emits Access-Control-Max-Age: 600. This is reflective CORS with credentials (any origin accepted, cookies allowed) — worth tightening to an explicit allow-list independent of performance.

Preflights cost 13–32 ms each and sit on the critical path of replay and events. Same-origin API (app.openreplay.com/api) would remove all 11.

2.4 Static assets from S3/CloudFront carry no Cache-Control#

133 static requests on app.openreplay.com; 126 have no Cache-Control header (only index.html says no-cache; the 7 assets.openreplay.com proxy responses are immutable). Consequences on this navigation: 8 hashed chunks re-validated with 304 (/assets/ui-*.js, index-*.css, SessionItem-*.js, ...), 66 served from memory cache only because the tab was still warm, and every hashed chunk is subject to heuristic expiry. Fix: Cache-Control: public, max-age=31536000, immutable on /assets/* (S3 object metadata or a CloudFront response-headers policy). The document response also shows x-cache: Error from cloudfront — the SPA fallback is served through a custom error response; harmless but worth knowing when reading CloudFront metrics.

Lazy chunks pulled in for the replay route (all brotli, first visit): player.module 90 KB, generateCategoricalChart 89 KB (recharts), PlayerInst 84 KB, html2canvas 40 KB, PlayerContent 20 KB, Session 10 KB — 477 KB total. Recharts and html2canvas load eagerly although no chart or screenshot is on screen.

2.5 The sessions-list boot set is fetched on a replay page#

/v2/filters (26 KB), /sessions/search/saved, POST /sessions/search (10 rows with full Session objects) and /sessions/search/ids page 2 all fire here. They come from route-agnostic effects (PrivateRoutes.tsx:249-266, Router.tsx:179-191) analysed in the 65/sessions report. On this page only prev/next navigation reads any of it (sessionStore.ts:498-504 → QueueControls.tsx:23-24), and it only needs ids. The page-2 search/ids call is a mount race: QueueControls.tsx:37-51 runs before page 1 has been applied, sees total = 0, sessionIds = [], and index === sessionIds.length - 1 is -1 === -1 → fetches page 2 unconditionally.

2.6 Per-request auth floor#

Python EE (ee/api/auth/auth_jwt.py:52-89, ee/api/auth/auth_project.py:19-48): async def dependencies calling synchronous psycopg2 on the event loop. Non-project routes pay 1 uncached query (users.auth_exists, ee/api/chalicelib/core/users.py:866-889); project routes pay 3 (auth_exists + projects.is_authorized + projects.get_project, all uncached). Each PostgresClient block is BEGIN/SELECT/COMMIT. Every response is then parsed and re-serialised by ORRoute (ee/api/or_dependencies.py:58-62). EE removed the 600 s cache FOSS has on notifications.get_all_count. /limits (constant body) at 34 ms and /2325/metadata (a PK lookup on a row auth already read twice) at 80 ms measure this floor.

Go (backend/pkg/server/auth/middleware.go:56 → ee/backend/pkg/server/user/storage.go:10-24): 1 uncached PG query per request (users ⋈ tenants ⋈ roles). EE tracer (ee/backend/pkg/server/tracer/middleware.go:31-46) does io.ReadAll(r.Body) on every request including GETs.

2.7 Third-party scripts on the replay route#

  • Cloudflare Turnstile (frontend/index.html:46, ?compat=recaptcha): loaded on every route at 159 ms; consumers are only signup/forgot-password forms.
  • Stripe js.stripe.com/v3 at 193 ms plus an iframe at 1,233 ms: not referenced anywhere in frontend/ (only an env placeholder frontend/env.ts:25) → SaaS-private billing module mounting globally. Should not load on a replay page.

3.2 GET /v2/{project}/sessions/{id}/events — 1,065 ms, 45.7 KB — the bottleneck#

Frontend. SessionService.getSessionEvents (SessionService.ts:115-120) ← sessionStore.addSessionEvents (sessionStore.ts:378-467), fired from fetchSessionData after replay resolves (sessionStore.ts:366) although only sessionId is needed. On completion Session.addEvents (session.ts:462-565) rebuilds the session object and WebPlayer.updateLists pushes per-tab lists into the player (player/src/web/WebPlayer.ts:177-192). Blocked on it: timeline loading stripes and markers (Controls/Timeline.tsx:39,146, EventsList.tsx:15-21), Events sidebar (EventsBlock.tsx:36-41), X-Ray lists (OverviewPanel.tsx:147-168), DevTools Events panel, Page Insights.

Backend. backend/pkg/events/api/handlers.go:46-123. Sequential prelude of 3 PG round trips before ClickHouse: auth; sessions.IsExists (session.go:210-219, SELECT EXISTS(… WHERE session_id = $1 AND project_id = $2)); sessions.GetPlatform (session.go:222-229, SELECT platform FROM public.projects WHERE project_id = $1 — the project is already cached in-process + redis by the projects service). Then 5 goroutines, 6 ClickHouse queries, all against product_analytics.events with WHERE session_id = ? AND project_id = ? and no time bound:

Q1 (events.go:233-252, then Q2 sequentially in the same goroutine):

SELECT created_at, "$properties" AS props, "$event_name" AS type, "$duration_s" AS duration,
       "$current_url" AS url, "$referrer" AS referrer
  FROM product_analytics.events
  WHERE session_id = ? AND project_id = ?
    AND "$event_name" IN ('CLICK', 'INPUT', 'LOCATION') AND "$auto_captured"
  ORDER BY created_at;

Q2 click-rage issues (events.go:468-489), Q3 errors (events.go:299-319), Q6 incidents (events.go:500-522): each a "$event_name" = 'ISSUE'/'ERROR' filter reading single JSON subcolumns — cheap.

Q4 custom events (events.go:329-364) — no $event_name predicate, reads both whole JSON objects:

SELECT "$properties" AS auto_props, properties, created_at, 'CUSTOM' AS type, "$event_name" AS name
  FROM product_analytics.events
  WHERE session_id = ? AND project_id = ? AND NOT "$auto_captured"
  ORDER BY created_at;

Q5 issues (events.go:395-418) — the suspect:

SELECT DISTINCT ON (events.created_at, issue_id) events.created_at AS created_at,
       issue_id, issue_type, context_string
    FROM experimental.issues
    INNER JOIN product_analytics.events ON (events.issue_id = issues.issue_id)
    WHERE session_id = ? AND events.project_id = ? AND issues.project_id = ?
      AND "$event_name" = 'ISSUE' AND issue_type != 'incident'
    ORDER BY created_at;

experimental.issues is ORDER BY (project_id, issue_id, type) and is filtered only by project_id, so ClickHouse streams every distinct issue of project 2325 (with context_string) to probe the hash built from the session's ISSUE events. Cost scales with the project's issue history, not with the session. The join is unnecessary: ingest already writes context_string into the ISSUE event's $properties (backend/pkg/db/clickhouse/connector.go:685).

Errors from any lane are logged and swallowed — a ClickHouse timeout returns 200 with empty arrays.

Table state. product_analytics.events in the current schema is ReplacingMergeTree(_timestamp, _is_deleted) PARTITION BY toYYYYMMDD(created_at) ORDER BY (project_id, session_id, "$event_name", created_at, event_id) (clickhouse/create/init_schema.sql:238-300). Before commit bbfbc8d1f (2026-09-14) it was ReplacingMergeTree(_timestamp) with no PARTITION BY — one giant partition. That commit adds product_analytics.events_v2 with the partitioned layout and a mirror MV (1.28.0/1.sql), but no Go code references events_v2, so prod still queries the old table. session_id is the 2nd key column, so per-session lookups do prune by primary key; the number of unmerged parts and Q5's project-wide stream are what cost.

Why ~1.1 s (ranked, unverified without system.query_log): Q5's project-wide experimental.issues scan + hash join + DISTINCT ON; six separate queries each paying parse/plan/part selection with whole-JSON materialisation on Q1/Q4; Q1→Q2 sequential; 3 sequential PG round trips before CH starts; unpartitioned table with many parts and no created_at bound.

Response shaping. events[] is 42.7 KB of the 45.7 KB (136 CLICK + 47 LOCATION). Per item: createdAt (ISO) and timestamp (ms); CLICK label = full antd class chains; host derived server-side from url; webVitals is a JSON string inside JSON with stringified numbers; explicit nulls for hesitation/selector/label. issues[] and userEvents[] duplicate each other: the tracker sends both CustomEvent and CustomIssue for the same action (tracker/src/main/index.ts:566,578), ingest writes both (datasaver/web.go:29-47), and /events returns the pair twice (12 of 16 issues are custom with timestamps identical to the 12 userEvents). errors: [] and incidents: [] here.
