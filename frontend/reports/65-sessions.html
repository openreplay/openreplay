2. Cross-cutting findings#

2.1 Go /v2/api responses are not compressed#

backend/pkg/server/api/responser.go:39-48 does json.Marshal → w.Write(body); the middleware chain (backend/pkg/server/middleware/builder.go:69: health → cors → auth → permissions → rateLimiter → auditTrail) has no compression. The only gzip code in the server package is request-body decompression (api/request.go:81-112). Responses also carry no Content-Length (chunked), no Cache-Control, no ETag.

The ingress annotation use-gzip: "true" (scripts/helmcharts/vars.yaml:101) is an ingress-nginx key; the chart uses the NGINX Inc. controller (nginx.org/* annotations), which ignores it. Observed headers confirm: no content-encoding on any /v2/api response.

Python already has GZipMiddleware(minimum_size=1000) (api/app.py:92), which is why only /projects (4,984 B) came back gzipped.

Measured savings (gzip -6 on captured bodies):

Response Raw gzip Saving
/v2/api/65/filters 25,018 5,385 78 %
/v2/api/65/sessions/search/saved 9,629 1,384 86 %
/v2/api/65/sessions/search 5,309 1,086 80 %
Go total 39,956 7,855 80 %

Total API wire for the page drops from 44.6 KB to ~12.5 KB by adding one middleware (gzhttp from github.com/klauspost/compress, already in go.mod:28).

2.2 Per-request auth cost#

Python (api/auth/auth_jwt.py:41-60): JWTAuth.__call__ is async def but calls synchronous psycopg2 code directly — users.auth_exists() (api/chalicelib/core/users.py:583-596, uncached, 1 query per request) and users.get_user() (cached 60 s). ProjectAuthorizer.__call__ (api/auth/auth_project.py:19-27) does the same with projects.get_project() (uncached). FastAPI runs async dependencies on the event loop, so every DB round-trip in auth blocks uvicorn's single event loop (api/entrypoint.sh: one process, no --workers). Handler bodies run in the threadpool, but auth is serialised across all concurrent requests. Evidence: /api/limits returns a hard-coded dict (api/routers/core.py:717-724) and still costs 33–57 ms; the five parallel Python calls form a staircase (22 → 33 → 57 → 59 → 69 ms in run 1).

Each with pg_client.PostgresClient() as cur: block also commits on exit (api/chalicelib/utils/pg_client.py:150) with psycopg2's default implicit BEGIN, so one SELECT costs three wire statements. Over the 5 boot requests: 7 queries, 6 of them auth, 5 of them the identical auth_exists SELECT on the same row.

Every JSON response is additionally serialised, parsed back, walked, and re-serialised by ORRoute.custom_route_handler (api/or_dependencies.py:61-65, helper.cast_session_id_to_string).

Go (backend/pkg/server/auth/middleware.go:15-86 → user/storage.go:9-20): 1 uncached PG query per request (SELECT user_id, name, email, ... jwt_iat FROM public.users WHERE user_id = $1 ...). No redis, no in-process cache. permissions and tracer middlewares are no-ops in FOSS. Note: validateProjectAccess (auth/authorizer_tenant.go:39-41) returns nil — consistent with the Python side (projects.get_project only checks existence), i.e. FOSS has no per-project ACL by design.

2.3 Frontend sends what the backend ignores#

POST /sessions/search body: {"filters":[],"rangeValue":"LAST_24_HOURS","startDate":…,"endDate":…,"sort":"startTs","order":"desc","viewed":false,"eventsOrder":"then","limit":10,"startTimestamp":…,"endTimestamp":…,"page":1}. The Go struct SessionsSearchRequest (backend/pkg/analytics/model/model.go:173-184) binds only filters, startTimestamp, endTimestamp, sort, order, eventsOrder, limit, page, series, bookmarked. rangeValue, startDate, endDate, viewed are dropped by json.Unmarshal. startDate/endDate also disagree with startTimestamp/endTimestamp (the latter are recomputed from Date.now() rounded to 15 min in search.ts:144-151,208-216).

GET /sessions/search/saved?limit=200: frontend constant SAVED_SEARCH_PAGE_SIZE = 200 (mstore/searchStore.ts:27) with a comment saying the whole list is loaded at once. Go handler (backend/pkg/analytics/saved_searches/handlers.go:153-159) accepts limit only if 0 < l <= 100, otherwise silently falls back to 20 — response echoes "limit": 20. The modal then pages locally at 100 (SavedSearchModal.tsx:29,67) and shows total from the server. Silent truncation once a project has > 20 visible saved searches (not visible today: 5 rows).

3.2 GET /api/projects — 22 ms, 4,984 B (gzip → 1,255)#

Frontend. ProjectsService.fetchList (services/ProjectsService.ts:14-17) → projectsStore.fetchList (mstore/projectsStore.ts:149-185) → new Project(d); the constructor keeps only declared keys (mstore/types/project.ts:23-28). Fired from Router.tsx:93 after account resolves.

Backend. core_dynamic.py:235-237 → projects.get_projects(tenant_id, gdpr=True, recorded=True) (api/chalicelib/core/projects.py:66-120), @cached 20 s per process. SQL (f-string expanded):

SELECT *, first_recorded IS NOT NULL AS recorded FROM (
    SELECT s.project_id, s.name, s.project_key, s.save_request_payloads, s.first_recorded_session_at,
           s.created_at, s.sessions_last_check_at, s.sample_rate, s.platform,
           (SELECT count(*) FROM projects_conditions WHERE project_id = s.project_id) AS conditions_count,
           s.gdpr,
           COALESCE(EXTRACT(EPOCH FROM s.first_recorded_session_at) * 1000::BIGINT,
                    (SELECT MIN(sessions.start_ts)
                     FROM public.sessions
                     WHERE sessions.project_id = s.project_id
                       AND sessions.start_ts >= (EXTRACT(EPOCH FROM COALESCE(s.sessions_last_check_at, s.created_at)) * 1000 - %(check_delta)s)
                       AND sessions.start_ts <= %(now)s)) AS first_recorded
    FROM public.projects AS s
    WHERE s.deleted_at IS NULL
    ORDER BY s.name ) AS raw;

Two problems:

  1. Dead persistence path. The follow-up UPDATE public.projects SET sessions_last_check_at = now(), first_recorded_session_at = … (projects.py:109-114) is gated on r["sessions_last_check_at"] is not None (:101). The only writer of sessions_last_check_at in the whole repo is this UPDATE (grep over api/, backend/, scripts/schema: readers only in health.py; column added NULL DEFAULT NULL in 1.8.0/1.8.0.sql:24). So the gate is never true, first_recorded_session_at is never persisted, and the correlated MIN(sessions.start_ts) subquery against the largest PG table runs for every un-recorded project on every cache miss, forever. Same code in ee/api/chalicelib/core/projects.py:108-122.
  2. projects_conditions has no index on project_id (FK only, init_schema.sql:1089); the correlated count(*) is one seq scan per project row.

Fetched and dropped before response: first_recorded_session_at, first_recorded, sessions_last_check_at (:106-108). Cache is never invalidated on create/edit/delete (stale list up to 20 s after POST /projects).

3.4 GET /api/notifications/count — 38 ms, 23 B#

Frontend. UserService.getNotificationsCount → notificationStore.fetchNotificationsCount (mstore/notificationStore.ts:95-102). Fired from TopHeader.tsx:22; re-polled every 5 min (Notifications.tsx:23-33). The value (1795) is rendered as <Badge dot={count > 0}> — a boolean.

Backend. core.py:614-616 → notifications.get_all_count (notifications.py:34-50), @cached 600 s:

SELECT COALESCE(COUNT(notifications.*), 0) AS count
FROM public.notifications
    LEFT JOIN (SELECT notification_id
               FROM public.user_viewed_notifications
               WHERE user_viewed_notifications.user_id = %(user_id)s) AS user_viewed_notifications USING (notification_id)
WHERE (notifications.user_id IS NULL OR notifications.user_id = %(user_id)s)
  AND user_viewed_notifications.notification_id IS NULL;

Anti-join over every notification visible to the user; grows unbounded with alert history (only creator is alert firing, alerts.py:138). The 10-minute cache is never popped: view_notification (notifications.py:53-76) and create (:79) don't touch it, so after "mark as read" the frontend's immediate refetch (notificationStore.ts:57,79) gets the stale count for up to 10 min. Cache masks query cost at the expense of correctness.

Verdict: only count > 0 is needed; an EXISTS … LIMIT 1 or a per-user watermark (users.notifications_seen_until) makes this O(1). Fold into boot payload.

3.6 GET /v2/api/65/filters — 99 ms, 25,018 B — the bottleneck#

Frontend. FilterService.fetchFilters (services/FilterService.ts:37-40) → filterStore.fetchFilters (mstore/filterStore.ts:442-470) → processFilterResponse (:472-545). Fired from PrivateRoutes.tsx:255-259; cached per project in memory (:447-449) and not refetched on SPA navigation — only on reload, project switch, or force=true after segment/tag saves. Gates sessions/search via filtersLoaded (§1.1).

Backend. filters_catalog/api/handlers.go:32,51-75 getAllFilters → projects.GetProject (in-process 5 min + redis 10 min cache) → GetAllFilters (filters_catalog/aggregator.go:10-41), which runs five sources strictly sequentially (no goroutines):

(a) ClickHouse — events catalog (ch_events.go:15-26):

SELECT DISTINCT ON(event_name, auto_captured)
    COUNT(1) OVER () AS total, event_name AS name, aec.display_name AS display_name, auto_captured
FROM product_analytics.all_events
    LEFT JOIN product_analytics.all_events_customized AS aec USING (project_id, auto_captured, event_name)
WHERE project_id = ? AND (aec.status = 'visible' OR aec.status = '')
ORDER BY auto_captured, aec.display_name, all_events.event_name

(b) ClickHouse — properties catalog (ch_properties.go:11-31):

SELECT COUNT(1) OVER () AS total, property_name AS name, apc.display_name AS display_name,
       event_properties.auto_captured_property AS auto_captured, possible_types
FROM product_analytics.all_properties
    LEFT JOIN product_analytics.all_properties_customized AS apc USING (project_id, source, property_name, auto_captured)
    LEFT ANY JOIN (
        SELECT property_name, auto_captured_property,
               arrayDistinct(groupArray(event_properties.value_type)) AS possible_types
        FROM product_analytics.event_properties
        WHERE event_properties.project_id = ?
        GROUP BY ALL
    ) AS event_properties USING (property_name)
WHERE project_id = ? AND (apc.status = 'visible' OR isNull(apc.status))
GROUP BY ALL
ORDER BY apc.display_name, all_properties.property_name

(c) metadata — projects.GetProject again (cache hit), no SQL. (d) Postgres — segments (pg_segments.go → saved_searches.go:389-412): SELECT search_id, name, is_public FROM public.saved_searches WHERE project_id=$1 AND deleted_at IS NULL AND is_share=FALSE AND (user_id=$2 OR is_public) ORDER BY name. (e) Postgres — features (pg_features.go → tags/admin/service.go:226-246): SELECT tag_id, name, selector, ignore_click_rage, ignore_dead_click, location FROM public.tags WHERE project_id=$1 AND deleted_at IS NULL ORDER BY name. (f) static session/user/users sections are rebuilt on every call (sessions.go:8-188: two copies of the 249-entry country list, ~40 MD5 StringToID computations).

Round-trips: 1 PG (auth) + 2 CH + 2 PG, all sequential. None of the catalog sources is cached — autocomplete_cache.go (180 s TTL) serves only the /events/autocomplete and /properties/autocomplete endpoints.

Probable correctness bug in (b). apc.status is LowCardinality(String) DEFAULT 'visible' — non-nullable (clickhouse/create/init_schema.sql:539). With ClickHouse's default join_use_nulls=0, a non-matched LEFT JOIN yields '', never NULL, so isNull(apc.status) is always false and only properties that have an explicit all_properties_customized row pass. The events query correctly uses aec.status = ''. The captured payload supports this: event.list contains exactly 3 items without the isPredefined key (label, url, urls) — the CH rows — and 25 predefined fallbacks from ch_properties.go:142-165 with possibleValues: []. Verify on prod with SELECT value FROM system.settings WHERE name='join_use_nulls'. If confirmed, the fix is one token (apc.status = ''), and the 25 KB payload will change shape.

CH schema alignment. all_events / all_properties / event_properties are ReplacingMergeTree catalogs fed by materialised views whose GROUP BY ALL includes created_at (init_schema.sql:735-769), so they accumulate one row per (name, created_at) per insert block until background merges collapse them. event_properties therefore scales with event volume between merges, and the GROUP BY ALL subquery in (b) is the most likely source of the ~100 ms. all_properties is additionally PARTITION BY toYYYYMM(_timestamp) — a catalog partitioned by insert month, so one part-set per month of history is read on every call.

C. Capture script (Playwright 1.61, CDP)#

const { chromium } = require('playwright');
const fs = require('fs');
const JWT = process.env.JWT;

(async () => {
  const browser = await chromium.launch({ headless: true });
  const ctx = await browser.newContext();
  const page = await ctx.newPage();
  const cdp = await ctx.newCDPSession(page);
  await cdp.send('Network.enable');

  const reqs = new Map();
  cdp.on('Network.requestWillBeSent', (e) => reqs.set(e.requestId, {
    url: e.request.url, method: e.request.method, type: e.type,
    startTs: e.timestamp, postData: e.request.postData || null,
  }));
  cdp.on('Network.responseReceived', (e) => Object.assign(reqs.get(e.requestId) || {}, {
    status: e.response.status, timing: e.response.timing, headers: e.response.headers,
  }));
  cdp.on('Network.loadingFinished', (e) => Object.assign(reqs.get(e.requestId) || {}, {
    endTs: e.timestamp, encodedDataLength: e.encodedDataLength,
  }));

  await page.goto('https://foss.openreplay.com/', { waitUntil: 'networkidle' });
  await page.evaluate((jwt) => window.setJWT(jwt), JWT);
  await page.waitForTimeout(1500);
  reqs.clear();

  await page.goto('https://foss.openreplay.com/65/sessions', { waitUntil: 'networkidle' });
  await page.waitForTimeout(4000);

  const out = [];
  for (const [id, r] of reqs) {
    if (/\/api\//.test(r.url)) {
      const b = await cdp.send('Network.getResponseBody', { requestId: id });
      r.body = b.base64Encoded ? Buffer.from(b.body, 'base64').toString() : b.body;
    }
    r.durationMs = Math.round((r.endTs - r.startTs) * 1000);
    out.push(r);
  }
  fs.writeFileSync('requests.json', JSON.stringify(out, null, 2));
  await browser.close();
})();
